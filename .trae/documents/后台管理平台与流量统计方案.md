# 后台管理平台 + 流量统计（GA4）实施文档

> 本文档由原「方案」更新而来，描述**当前代码库的实际实现**。
> 与原方案的关键差异：内容存储未采用「全量入 Supabase」，而是自建 Store 抽象（Upstash Redis / 本地 JSON）；认证未采用 Supabase Auth，而是单密码 Cookie 认证。Supabase 降级为可选只读数据源。

---

## 一、背景与目标

站点是一个纯静态 SSG 的 Next.js 15 外贸官网（45 页预渲染，SEO/GEO 优化完善）。原内容硬编码在 `lib/*.ts` 静态文件里。需要新增：

1. **流量来向统计** —— 接入 GA4。
2. **后台管理平台** —— 在线编辑产品、品类、文章、FAQ、公司信息。

核心约束不变：**不破坏现有 SEO/GEO 能力**（静态 HTML 预渲染、JSON-LD、canonical、sitemap、llms.txt、AI 爬虫白名单）。前台渲染从纯 SSG 改为 **ISR（增量静态再生成）**，编辑后按需刷新。

---

## 二、实际架构总览

```
前台读（lib/queries.ts，三层降级）：
  getProducts() 等 → ① Store（Redis → data/*.json）
                    → ② Supabase（可选，仅当配置了 env 且表内有数据）
                    → ③ 静态 seed（lib/products.ts 等）

后台写（Server Actions）：
  表单 → app/admin/actions.ts → Store（Redis 或 data/*.json）
       → revalidatePath() 触发前台 ISR 刷新
```

关键点：**后台编辑只写 Store，不写 Supabase**。Supabase 仅作为可选的只读数据源保留（当前未配置时完全不参与）。

---

## 三、架构决策（实际）

| 决策点 | 实际选择 | 说明 |
|---|---|---|
| 内容存储 | Store 抽象：Upstash Redis（生产）/ 本地 `data/*.json`（本地离线） | Vercel 文件系统只读，故生产用 Redis REST；本地开发直接读写 JSON 文件 |
| 认证 | 单密码 Cookie 认证（`ADMIN_PASSWORD`） | 根目录 middleware 比对 cookie；无 Supabase Auth |
| 前台渲染 | ISR + `revalidatePath` | 保留静态 HTML 的 SEO 优势，编辑后按路径刷新 |
| Supabase | 可选只读数据源（未配置则完全跳过） | schema.sql / setup-db.ts / seed.ts 均保留 |
| GA4 | `@next/third-parties/google` 的 `GoogleAnalytics` | 官方组件，自动处理加载 |
| 复杂字段 | JSON 文本块编辑 | 表单中 JSON 编辑区，Server Action 侧 `JSON.parse` 校验 |

## 四、内容存储层（`lib/store.ts`）

- Redis 连接：`UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN`（或 Vercel KV 等价变量 `KV_REST_API_URL`/`KV_REST_API_TOKEN`）。
- 读：`readCollection(name)` → 先 Redis（key 前缀 `yunhongtex:`），失败/未配置回退 `data/<name>.json`。
- 写：`writeCollection(name, data)` → 有 Redis 写 Redis，否则写 `data/<name>.json`。
- 五个集合：`categories` / `products` / `articles` / `faqs` / `site`，对应 `getStore*` / `setStore*` 十个函数。
- `isRemoteStore()`：供后台仪表盘展示当前存储模式。
- `ensureSeeded(seed)`：预留的幂等 seeding 工具（当前代码中**尚无调用方**）。

---

## 五、数据访问层（`lib/queries.ts`）

- 类型统一在 `lib/types.ts`（`Product`/`Category`/`Article`/`Faq`/`Site` 等）。
- 每个集合一个 `loadXxx()`，按 ① Store → ② Supabase（`lib/supabase/anon.ts`，不触碰 cookie，保证前台仍可静态预渲染）→ ③ 静态 seed 的顺序返回数据。
- `mapXxx()` 同时兼容 camelCase（JSON/Redis）与 snake_case（Supabase 列名）。
- 对外 async 函数：`getCategories()`、`getCategory(slug)`、`getProducts()`、`getProduct(slug)`、`getProductsByCategory(slug)`、`getFeaturedProducts()`、`getRelatedProducts(slug, limit)`、`getArticles()`、`getArticle(slug)`、`getRecentArticles(limit)`、`getFaqs()`、`getSite()`。
- 所有 loader 用 React `cache()` 包裹：同一渲染（layout + header + footer + 页面 + generateMetadata）内每个集合只读一次 store，请求间自动失效，与 `revalidatePath` 配合无一致性问题。
- 查询函数**未使用** `next: { tags }` + `revalidateTag`，刷新靠 Server Actions 里的 `revalidatePath`（见第九节）。
- 静态文件 `lib/products.ts`（1112 行）、`lib/articles.ts`、`lib/faqs.ts`、`lib/site.ts`（`defaultSite`）保留，作为 seed 来源。

---

## 六、认证与路由保护（根目录 `middleware.ts`）

- matcher：`/admin/:path*` 与 `/api/admin/:path*`（API 未认证时返回 401 JSON）。
- 校验逻辑：cookie `admin_auth` 的值 === `ADMIN_PASSWORD` 的 SHA-256 哈希。**未配置 `ADMIN_PASSWORD` 时 fail closed**（后台完全锁定，无 fallback 密码）。
- 登录：`adminLogin` Server Action 用 `timingSafeEqual` 比对哈希，成功后由服务端写入 **httpOnly + SameSite=Lax +（生产）Secure** 的 cookie（7 天），cookie 内只有哈希、不含明文密码。
- `adminSignOut` 服务端删除 cookie 后重定向到 `/admin/login?logout=1`；已登录访问登录页会重定向回 `/admin`。

## 七、前台页面改造（保持 SEO 输出不变）

- 三个动态路由页 `app/(site)/products/[slug]/page.tsx`、`app/(site)/fabrics/[category]/page.tsx`、`app/(site)/insights/[slug]/page.tsx`：
  - `generateStaticParams` 改为 `async`（从 `lib/queries.ts` 查 slug）；
  - `dynamicParams = true`（后台新增内容可动态生成）；
  - 页面组件 `await getXxx()`。
- 列表页/静态页（首页、fabrics、faq、insights、quality、not-found 等）：静态数组顶层 import 改为组件内 async 查询。
- `app/sitemap.ts` 改为 `async`，从查询层读数据；`lastmod` 取 `data/*.json` 的最新 mtime（后台编辑后自动反映真实新鲜度，替代原来的硬编码日期）。`app/llms.txt/route.ts` 同样 async 化。
- 客户端组件（如 `rfq-form.tsx`）不直接查 DB，由父页面（server）查好数据作为 props 传入。
- `lib/site.ts` 保留 `defaultSite` + 纯函数（`absoluteUrl`/`whatsappLink` 等）；`getSite()` 将 Store 里的 site 合并到 `defaultSite`（DB 值优先，缺失字段用默认值）。

## 九、Server Actions（`app/admin/actions.ts`）

- 写入函数：`saveCategory`、`saveProduct`、`saveArticle`、`saveFaq`、`saveSiteSettings`；删除函数：`deleteCategory`、`deleteProduct`、`deleteArticle`、`deleteFaq`。
- 模式：读取 Store 当前数组 → 按 `id`（slug 或 FAQ 索引）定位更新或追加 → `setStore*` 写回。
- 复杂字段（intro/highlights/sections/faqs 等）通过 `parseJson()` 校验，非法 JSON 返回表单错误。
- 写成功后调用 `revalidateContent()`：`revalidatePath` 覆盖 `/`、`/fabrics`、`/fabrics/[category]`、`/products/[slug]`、`/insights`、`/insights/[slug]`、`/faq`、`/quality`，再 `redirect` 回列表页。
- FAQ 保存/删除只刷新 `/`、`/faq`、`/quality`。
- 认证相关：`adminLogin`（SHA-256 哈希 + `timingSafeEqual` 比对，服务端写 httpOnly cookie）、`adminSignOut`（服务端删 cookie）。
- 前台另有 `app/actions.ts` 的 `submitRfq`（RFQ 询盘表单）：服务端校验 + 蜜罐反垃圾 + **按 IP 限流（10 分钟 3 次，进程内存）**。配置 `RESEND_API_KEY`/`RESEND_FROM`/`RFQ_TO` 后经 Resend 发送**品牌化 HTML 邮件**（销售通知 + 买家自动确认回执两封），未配置时仅 console 日志。提交成功后同时向 GA4 发服务端转化事件（Measurement Protocol，可选）。

## 十、GA4 接入

- `app/(site)/layout.tsx` 的 `<body>` 内挂 `<GoogleAnalytics gaId={process.env.NEXT_PUBLIC_GA_ID} />`。
- 后台仪表盘根据 `NEXT_PUBLIC_GA_ID` 生成 GA4 报告入口链接（数据本身在 Google Analytics 后台查看，站内不建图表）。
- **转化事件**：
  - 客户端（`lib/analytics.ts` 的 `trackEvent`，gtag 未加载时安全空转）：`whatsapp_click`（header/footer/首页/联系页/RFQ 成功页的 WhatsApp 链接，带 `location` 参数，经 `components/whatsapp-link.tsx` 客户端组件统一埋点）、`generate_lead`（RFQ 提交成功）。
  - 服务端（Measurement Protocol，`app/actions.ts`）：RFQ 提交成功后上报 `generate_lead`（含 product/company/country 参数），需要 `GA4_MP_API_SECRET`，访客屏蔽 gtag 时依然准确。

## 十一、Supabase（可选路径）

- `supabase/schema.sql`：categories/products/articles/faqs/site_settings 建表 + RLS（公开读、认证写）。
- `scripts/setup-db.ts`：用 `pg` 直连数据库执行 schema.sql（绕过 SQL Editor 限制），需要 `.env` 里的 `NEXT_PUBLIC_SUPABASE_URL` + `DB_PASSWORD`。
- `scripts/seed.ts`：用 `service_role` key 把静态目录写入 Supabase 表（幂等，按 slug upsert）。
- `lib/supabase/`：`anon.ts`（只读匿名客户端，未配置 env 返回 null）、`server.ts`（绑定 cookie 的服务端客户端）、`client.ts`（浏览器端客户端）。
- 说明：前台查询层仅在「Store 无数据」且「Supabase 已配置且表内有数据」时才使用 Supabase；**后台编辑不会写入 Supabase**。

| 脚本 | 用途 |

## 十五、已知问题与注意事项

1. **图片为 AI 生成图（已自托管）**：全部产品/品类/文章图片已从外部生成服务迁移为 `public/images/` 自托管静态文件（`lib/utils.ts` 的 `fabricPhoto()` 按 FNV-1a 哈希定位，OG 图经 `absoluteUrl` 输出绝对 URL）。但图片本身仍是 AI 生成图，上线前需替换为真实面料实拍图。
2. **联系信息占位符**：`defaultSite` 中 phone/whatsapp 为占位号码、social 链接为空，上线前必须填入真实信息（可通过后台 Settings 修改，或改 `lib/site.ts` 默认值）。
3. **数据一致性**：后台编辑只写 Store（Redis/JSON），永不写入 Supabase；若未来重新启用 Supabase 作为主数据源，需先迁移 Store 数据。
4. **死代码**：`ensureSeeded()` 当前无调用方；`lib/supabase/client.ts`（浏览器端 client）当前无引用。
5. **RFQ 邮件通道**：已支持 Resend（`RESEND_*` 变量）并可回退 console 日志；限流为进程内存级（serverless 冷启动即重置），高流量下需换 Redis 限流。
6. **FAQ 编辑定位**：FAQ 无 slug，以数组索引定位，删除后索引会漂移，批量操作需留意。
7. **错误边界**：已补 `app/global-error.tsx`（根级）与 `app/(site)/error.tsx`（前台页面级）；admin 区暂无独立 error 边界。

## 十六、验证方式（实际可用）

- `npm run typecheck`、`npm run build` 通过。
- 本地：`npm run seed:json` 生成 `data/*.json` → `npm run dev`。
- 访问 `/admin`：未登录跳转 `/admin/login`；输入 `ADMIN_PASSWORD` 登录进入仪表盘。
- 后台编辑某产品价格 → 前台 `/products/<slug>` 刷新后显示新值（本地看 `data/products.json` 已更新；生产看 Redis）。
- SEO 输出核对：`/sitemap.xml`、`/llms.txt`、`/robots.txt`、产品页 JSON-LD/canonical 与改造前一致。
- GA4：DevTools Network 中出现 `googletagmanager.com` 请求。
